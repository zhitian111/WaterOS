\chapter{总体架构设计}

\wateros{}采用组件化的单体内核结构。内存管理、调度、文件系统与网络等服务运行在同一
内核地址空间中，跨模块调用仍是普通函数调用；代码则按稳定职责拆成独立crate，通过明确
接口控制依赖方向。这样做的主要目的不是增加抽象层，而是把“谁拥有状态、谁决定策略、谁
负责清理”固定下来。发生跨模块故障时，可以沿对象所有权和调用链定位，而不必从系统调用
入口一路追查所有全局变量。

\section{系统分层与组件职责}

从硬件到用户程序，系统可以分为平台运行层、资源管理层、内核服务层、ABI入口层和用户
环境层。前四层位于内核中，用户环境层由独立的根文件系统构建组件生成。同一层的组件可以
互相协作，但长期状态只能由一个组件负责；上层通过句柄或稳定ID访问下层对象，不能复制
下层内部状态作为另一份事实来源。

\section{API、实现与聚合门面}

多数一级组件采用\code{api-v0 + impl-* + facade}的组织方式。\code{api-v0}只定义跨层可见
的trait、句柄、错误类型和数据结构，不依赖具体平台；\code{impl-*}持有可变状态并实现机制；
组件门面根据Cargo feature选择活动实现，再以稳定模块名导出。顶层内核只依赖
这些门面，不直接写入某个\code{impl-*}的全局状态。

这种划分需要满足三条规则：第一，接口只表达调用方真正需要的能力，不把实现内部容器暴露
出去；第二，同一策略的互斥实现由feature和\code{compile\_error!}保证只能选择一个；第三，
实现选择发生在构建期，运行期对象仍需经过初始化与发布，不能把“feature已启用”等同于
“设备或服务已经可用”。例如启用VirtIO块设备实现只表示代码被编译，实际设备仍需DTB或
PCI枚举成功后才进入注册表。

\section{依赖与调用方向}

组件依赖不是简单的自上而下树形结构。任务阻塞需要调度器，文件映射同时关联VFS和MM，
信号返回又连接task、IPC、syscall与trap。WaterOS对这种交叉关系采用“状态所有权不反转，
生命周期通过钩子接线”的办法：下游组件拥有对象，上游组件保存句柄；创建、复制、exec和
退出时，由明确的编排层依次通知相关侧表，而不是让底层组件相互反向依赖。

\subsection{文件读取调用链}

用户执行\code{read(fd, buf, len)}后，trap层只负责取出调用号和六个参数槽。syscall层检查fd、
长度和用户缓冲区，再从当前任务的fd表取得\code{SharedIoHandle}。普通文件经VFS页缓存和
\code{FsBridge}访问具体文件系统，缓存未命中时才由FS向块设备发起I/O。数据返回后，syscall
层逐页复制到用户地址；若跨页复制中途失败，VFS的读取租约只提交已成功复制的前缀，返回
部分字节数，未提交数据仍保留在对象中。

\subsection{进程创建与退出调用链}

fork不是task组件内的一次对象复制。编排层先创建TCB/PCB和子地址空间，MM把父进程私有可写
页建立为COW关系，VFS复制fd与cwd，cred复制凭证，IPC/signal建立子进程状态。所有侧表完成后，
子任务才发布到ready queue。退出时顺序相反：先撤销调度可见性并记录退出状态，再关闭任务级
资源、处理robust futex和共享内存附件，最后保留zombie供父进程wait；reap后才删除进程索引并
在锁外释放可能触发大量析构的地址空间和fd对象。

\subsection{文件映射与缺页调用链}

\code{mmap}先由syscall校验flag、权限、长度和offset。匿名映射直接交给MM建立VMA；文件映射
先从VFS取得稳定文件句柄和映射loader，再由MM记录后备关系。首次访问触发page fault，MM按
VMA类型填零、从文件读取或执行COW。共享可写文件页变脏后由VFS页缓存负责写回，VMA销毁只
撤销当前地址空间映射，不能在仍有缓存引用时直接释放底层文件页。

\subsection{网络收发调用链}

socket系统调用由syscall解析地址族和用户结构，INET socket交给network创建，并以VFS对象
进入fd表。发送时数据从用户页复制到协议栈，再由网卡驱动传输以太网帧；接收时network先
建立\code{SocketReceiveLease}，用户复制成功后才消费对应字节。协议栈当前由全局poller推进，
poll/阻塞调用会重扫状态；网卡事件还没有直接唤醒每个socket等待队列的完整链路。

\section{初始化与发布顺序}

启动必须遵循依赖顺序。堆和物理帧可用之前不能构造需要动态内存或DMA的设备；trap入口未
安装之前不能打开中断；任务侧表尚未初始化时不能发布第一个用户任务。BSP完成全局服务，
AP只初始化本CPU状态，最终通过online集合向调度器发布可用性。

\section{双架构适配边界}

RISC-V64路径使用OpenSBI、Sv39和DTB/VirtIO-MMIO；LoongArch64路径使用本地CSR/IOCSR、
独立三级页表以及PCI ECAM/VirtIO-PCI。二者共享task、VFS、FS、IPC、network和大部分
syscall实现。共享接口保证调用形式一致，但不自动保证硬件能力相同：RISC-V64已有远程TLB
失效路径，LoongArch64目前仍返回\code{Unsupported}。涉及页表并发修改、IPI、定时器和设备
枚举的验证必须分别执行，不能以一种架构的结果替代另一种。

\section{并发、错误与可观测性约定}

全局注册表通常只在锁内查询或克隆\code{Arc}，真正的设备I/O、文件系统操作和任务阻塞在
释放表锁后完成。可阻塞路径采用“检查条件—登记等待—释放对象锁—调度”的顺序，并在调度
临界区复查条件，以封住丢失唤醒窗口。创建路径先完成初始化再发布，销毁路径先撤销可见性
再释放资源，这两条顺序贯穿task、MM、VFS、IPC和network。

组件内部先保留原始错误语义，直到syscall边界才统一转换成errno。未实现调用返回
\code{ENOSYS}，设备或平台不具备的能力返回\code{Unsupported}，不会伪造成功。读写、pipe、socket和终端的
用户复制使用reservation/finish/cancel模式，使部分成功和copy fault都有明确结果。调试构建
按CPU记录调度、trap、IPI、futex、TLB和锁事件；普通构建保留低频状态与错误日志，避免
诊断本身改变高并发路径的行为。
