\chapter{项目概述}

\wateros{}是一个使用Rust编写的\code{no\_std}内核。目前项目以QEMU为主要运行环境，
支持RISC-V64和LoongArch64两种架构，并按照Linux generic 64-bit ABI向用户程序提供
系统调用。项目的目标不是逐项复刻Linux内部结构，而是实现一条能够持续运行实际用户
程序的内核主路径：程序可以从ext4根文件系统装载，在多核环境中创建进程和线程，通过
文件、管道、共享内存与socket交换数据，并在退出后正确回收资源。

随着系统逐步能够运行BusyBox、glibc/musl测试程序、CAgent以及编译类负载，开发重点也
发生了变化。早期工作主要是补齐单个系统调用；当前更需要处理跨组件状态，例如fork时
地址空间与文件描述符的继承、退出时任务与进程资源的回收、文件页缓存的写回，以及地址
空间在多个CPU之间切换时的TLB一致性。本文因此以这些实际执行路径为主线说明设计，测试
通过数量只作为实现结果的证据，不作为“完整兼容Linux”的替代说法。

\section{设计目标与约束}

WaterOS的设计工作围绕以下几项约束展开：

\begin{itemize}
  \item \strong{以用户态执行路径为边界。}系统调用入口、用户指针检查、内核对象和
  设备访问必须能够连成闭环；仅声明接口而没有后端实现，不视为功能完成。
  \item \strong{隔离平台差异。}RISC-V64和LoongArch64分别实现启动、异常、分页和
  中断等底层能力，任务、文件系统、网络与系统调用层尽量复用同一套接口。
  \item \strong{按生命周期管理资源。}任务进入就绪队列之前完成必要的关联状态，
  退出后按进程、地址空间、文件描述符和缓存对象各自的引用关系回收，避免多核环境下
  出现“对象已经可见但尚未初始化”或“仍被使用却提前释放”的情况。
  \item \strong{保留可复现的验证入口。}构建参数、根文件系统、QEMU配置和串口日志
  都由脚本保存；历史结果和当前候选版本的复测结果分开记录。
\end{itemize}

项目仍有明确的工程边界。当前只支持4 KiB页，不包含大页；网络协议栈以IPv4 TCP/UDP
为主；权限与capability尚未达到完整Linux语义；少用系统调用会返回\code{ENOSYS}。
这些限制不会妨碍已经接通的工作负载运行，但在评价兼容范围时需要单独说明。

\section{实现主线}

WaterOS早期以单架构启动和基础系统调用为主，许多功能可以通过一个小型用户程序单独
验证。随着BusyBox、glibc/musl测试程序和编译类负载接入，问题逐渐从“接口是否存在”
转向“多个对象能否保持一致”。例如，fork不仅要创建任务，还要处理地址空间、文件描述符、
凭证与信号状态；文件映射也不只是建立页表项，还涉及缺页装载、共享页缓存和写回时机。

因此，当前实现以用户程序实际经过的路径为主线。平台层先提供启动、异常、时钟和设备
访问能力，任务与内存管理建立进程执行环境，VFS、文件系统、网络和IPC维护用户可见对象，
系统调用层最后完成ABI参数与内部接口之间的转换。每条路径都要求创建、使用和销毁三个
阶段闭合，不能只以调用入口能够返回作为完成标准。

双架构支持也推动了这条主线的稳定。RISC-V64与LoongArch64保留各自的页表、中断、固件和
设备发现实现，上层组件则通过共同接口复用。这样既能避免把平台细节散落到通用代码中，
也能在测试时明确区分共享逻辑问题与架构适配问题。
