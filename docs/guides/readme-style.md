# README 编写规范

[项目首页](../../README.md) · [文档总览](../README.md) · [内核工程](../../os/README.md)

WaterOS 的 README 按页面层级使用不同的视觉和内容密度。标准化的目标是让读者快速确认
自己所在的位置并找到上级入口，而不是把项目首页复制到每个目录。

## 项目级页面

适用于根 `README.md`、`os/README.md` 和 `docs/README.md`。

- 根 README 使用完整 Hero、徽章、仓库入口和主导航；
- `os/` 与 `docs/` 使用高度 `72` 的紧凑校徽；
- 页面标题和一句话定位居中；
- Hero 下提供项目首页、内核工程、文档或工具入口；
- 详细信息通过链接引用唯一事实来源，不复制容易漂移的参数表。

## 组件级页面

适用于主要 `wateros-*` crate。

```markdown
# wateros-example

[项目首页](...) · [内核工程](...) · [系统架构](...)

> 或一段简洁的组件职责说明。
```

组件 README 不放校徽和徽章。正文根据实际内容组织，通常包括职责与边界、目录结构、
核心流程、并发或安全约束、Feature 与依赖、验证方式。

## 内部模块与文档索引

较深层的实现 crate、任务索引和工具专题只使用轻量导航：

- 第一项返回项目首页；
- 第二项返回所在领域的总览；
- 第三项链接最相关的上级组件或专题；
- 不复制根 README 的 Hero、比赛全称和技术徽章。

任务历史与实验报告应优先保留日期、状态、测量口径和证据，不为了视觉统一改写历史
结论。第三方 `os/vendor/` 中的 README 保持上游原貌，不应用 WaterOS 模板。

## 链接与事实来源

- 构建参数与常用命令以根 README 的“构建配置”为准；
- Makefile 设计以 `docs/tools/makefile.md` 为准；
- 脚本清单以 `os/scripts/README.md` 为准；
- 调试、热点分析等专题只在对应 `docs/tools/` 页面展开；
- 相对链接必须从当前 README 所在目录计算，并在提交前检查目标存在。

## 文风

- 先说明组件实际负责什么，再解释实现方式；
- 用肯定、具体的技术陈述代替宣传性形容词；
- 中英文技术术语保持一致，例如 Cargo feature、guest、syscall、snapshot；
- 不使用“AI 完成”等来源性措辞；
- 不承诺代码尚未实现或尚未验证的能力。
