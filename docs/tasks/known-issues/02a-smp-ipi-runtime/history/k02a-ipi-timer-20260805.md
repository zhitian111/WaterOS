# K-02A IPI、Timer 与 Idle 验证（2026-08-05）

## 方法

使用 `gdb-debug` 内核的 `WATEROS_DEBUG_STATE`，在定向 workload 完成后、busybox
`sleep` 保持 guest 存活期间抓取两次快照。快照间恢复 guest 运行，比较每 CPU
`timer_ticks`、`context_switches`、`ipi_sent/received`、idle 标志和五类 runqueue。

RISC-V 先完成 CPU1--7 各 10,000 次远端 wake（共 70,000 次）；LoongArch 先完成
10,000 次 CPU0/CPU1 remap/TLB shootdown。两架构均为 8 CPU。

## 结果

- LoongArch 两快照间每个 CPU 的 `timer_ticks` 均增加 1,384；8 核始终 idle，全部
  runqueue 为零。压测涉及的 CPU0--2 `ipi_received` 不再增加。CPU0 新发 14 次
  `Reschedule`，CPU3 恰好接收 14 次，有发送来源且无重复重入。
- RISC-V 两快照间每个 CPU 的 `timer_ticks` 均增加 887；8 核始终 idle，全部
  runqueue 为零。CPU2 到 CPU0 的 887 次 `Reschedule(mask=1, kind=1)` 来自
  `gdb-debug`/stall monitor 的周期唤醒，每次均有新发送，不是旧 pending 未清除。
- 两架构的 idle PC 均位于 `__wateros_idle_task_runtime_main`，无 runnable task 滞留、
  lock wait 或固定 pending IPI 导致的软中断重入。

因此当前 send/publish、trap clear、`take_pending_ipi` 和 scheduler reschedule 顺序满足
K-02A 的无 IPI storm 验收。调试 monitor 自身的跨核唤醒属于观测扰动，不存在于普通
release 配置，后续性能测试不使用该计数作为 release 开销基线。
