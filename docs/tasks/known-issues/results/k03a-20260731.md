# K-03A regex_search 阶段复验

## 本轮范围

按白天短测约束，仅复验 RISC-V64 glibc。未运行完整 libc-bench 四配置，也未据单配置
关闭 K-03A。

## 复现

从 `test_case/libc-bench/regex.c` 提取原始负载：

- 栈上 `260000` 字节缓冲区；
- 表达式 `(a|b|c)*d*b` 和 `a{25}b`；
- `regcomp`、单次 `regexec`、`regfree`；
- 补齐原 harness 的 `fork -> child benchmark -> waitpid` 结构。

程序使用 `riscv64-linux-gnu-gcc -O2 -static` 构建。Linux `qemu-riscv64` 对照和
WaterOS RISC-V64/OpenSBI 8 核均在 5/12 秒硬超时内运行。

## 结果

WaterOS 定向用例约 0.2 秒完成：

```text
K03A_SEARCH pattern=(a|b|c)*d*b result=0
K03A_WAIT pattern=(a|b|c)*d*b status=0 exited=1 code=0 signaled=0 signal=0
K03A_SEARCH pattern=a{25}b result=0
K03A_WAIT pattern=a{25}b status=0 exited=1 code=0 signaled=0 signal=0
K03A_REGEX_DONE first=0 second=0
```

日志中没有用户 fault、signal、panic 或 `BadFd`。原始 `/glibc/libc-bench` 在 12 秒
内运行到 `b_pthread_createjoin_serial2`，尚未进入 regex；这是前置 benchmark 工作量，
不能判为 regex 超时。

## 结论与剩余门禁

最新内核的 RISC-V glibc regex search、用户栈、fork/COW 和 wait 路径在该负载下正常，
本轮没有代码根因可修。仍需夜间运行 glibc/musl、RISC-V/LoongArch 四配置原始
libc-bench，确认均输出 regex time/score 后才能关闭 K-03A。本机没有 RISC-V musl
交叉编译器，不能用相同最小程序替代原始 musl 二进制的结果。
