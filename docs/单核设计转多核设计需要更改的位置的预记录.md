# 单核设计转多核设计需要更改的位置的预记录

## 记录口径

本文记录 2026-07-20 静态检查中发现的 UP 假设和 SMP 改造位置，目标是支持决赛要求的 RISC-V64 与 LoongArch64 `-smp 8 -m 8G`。这不是已实现说明。条目只有在双架构运行验证通过后才能标为完成。

建议先做一个粗锁、全局 ready queue 的正确性版本，再用测量结果拆锁。启动次核之前，必须先处理共享 boot stack、全局调度器、process registry、frame allocator 和内核堆递归检测，否则增加 `-smp` 会直接引入内存破坏或 panic。

## 1. 启动汇编和 BSP/AP 分流

### RISC-V64 启动入口

- 位置：`os/components/wateros-platform/platform-impl/impl-qemu-riscv64-opensbi/src/asm/_start.S`
- 现状：所有 hart 在 `_start` 处都执行 `la sp, boot_stack_top`，共用一份 64 KiB 栈，然后调用同一个 `kernel_main`。
- 风险：多个 hart 同时进入时会覆盖返回地址和 Rust 栈变量。Rust 层再 park 次核已经太晚，因为进入 `kernel_main` 前共享栈已经发生。
- 待改：按 hart id 选择独立栈；保留 `a0=hart_id` 和 `a1=dtb_pa`；BSP 进入全局初始化，AP 进入独立 `secondary_main`。栈数组至少覆盖 8 个 hart，并检查 hart id 上界。

### RISC-V64 次核策略

- 位置：`os/src/main.rs:110-119`、`132-146`
- 现状：非 0 hart 关闭中断后永久 WFI。
- 待改：BSP 完成全局对象初始化后发布 release 状态；AP 以 acquire 顺序等待，然后初始化本核 trap、页表、timer、idle task 并进入调度。需要定义启动失败和部分 CPU 离线时的行为。

### OpenSBI HSM

- 位置：`wateros-platform` 的 RISC-V platform impl，目前没有 HSM 封装。
- 待改：增加 hart start、status 和可选 stop 接口；确认 QEMU/OpenSBI 是由所有 hart 同时进入 payload，还是由 BSP 显式 HSM 唤醒，避免重复启动。把固件差异封装在 platform 层，不放进调度器。

### LoongArch64 启动入口

- 位置：`os/components/wateros-platform/platform-impl/impl-qemu-loongarch64-virt/src/asm/_start.S`、`os/src/main.rs:289-377`
- 现状：所有 CPU 使用同一个 `boot_stack_top`，Rust 入口没有 BSP/AP 识别或次核等待逻辑。
- 待改：确认 QEMU virt 固件传入的 CPU id 和启动协议；实现每核栈和 AP 入口；仅 BSP 执行 heap、driver、MM、FS 和用户进程全局初始化。

### 启动阶段同步

- 新增状态应至少区分 `Booting`、`GlobalsReady`、`SchedulerReady`、`Online` 和 `Failed`。
- 发布全局指针、页表 token、调度器和注册表之前必须使用 Release；AP 读取使用 Acquire。
- AP 不能重复执行 `runtime::heap_allocator::init()`、`task::init()`、驱动 probe、根文件系统挂载或用户 bring-up。
- panic 时应能打印 CPU id。一个 AP 启动失败时要么停止整机，要么从 online mask 移除并让 `/proc` 如实报告。

## 2. CPU 本地状态和公共接口

### CPU id 与在线集合

- 当前缺口：仓库没有 `current_cpu_id`、online CPU mask 或统一的最大 CPU 数接口。
- 待改：在 platform/base API 提供当前 CPU id、最大 CPU 数、online mask 和迭代接口。RISC-V 可在早期把 hart id 放入 `tp`，但切换用户 TLS 前必须明确内核如何保存和恢复 CPU-local 基址。LoongArch64 需要对应的 CPU-local 寄存器方案。

### HartLocal/CpuLocal 容器

建议由一个边界检查过的 `CpuLocal<T, MAX_CPUS>` 承载：

- current task 和 idle task
- scheduler tick、preempt/interrupt nesting depth
- heap recursion depth
- trap scratch、内核栈顶和当前地址空间 token
- per-CPU 统计与必要的临时缓冲

容器初始化必须支持静态未初始化状态，不能在 allocator 可用前依赖堆分配。

### CPU 报告

- 位置：`os/components/wateros-fs/fs-procfs/procfs-impl/impl-kernel/src/lib.rs:202-204`
- 现状：`/proc/cpuinfo` 固定只输出 processor 0。
- 待改：按 online mask 生成每个 CPU 段；`sched_getaffinity` 使用同一信息源；`nproc` 在 8 核评测下返回 8。不能只为测试硬编码数字。

## 3. 调度器和任务状态机

### 全局调度器容器

- 位置：round-robin `scheduler-impl/impl-round-robin/src/lib.rs:43-60`，multi-class `scheduler-impl/impl-multi-class/src/lib.rs:51-155`
- 现状：全局调度器放在 `UniprocessorSafeCell` 中，调用方只靠关闭本核中断避免重入。
- 风险：关本核中断不阻止另一核进入。`RefCell` 可能 panic，更严重时不安全 `Sync` 会掩盖数据竞争。
- 待改：使用真正的 SMP lock；把初始化发布和运行期锁分开；定义 scheduler lock 的 IRQ 保存规则和锁顺序。

### per-CPU current 和 idle

- 当前调度器把 current task 当作全局唯一状态。
- 待改：每核拥有 current 和 idle；idle 不进普通 ready queue；tick 只记到本核 current；`current_task_id()` 等 API 从 CPU-local 状态读取。

### 任务所有权不变量

任务状态需要能表达 `Running(cpu_id)`，并满足：

- 一个普通 task 最多被一个 CPU 持有
- Ready、Blocked、Sleeping、Exited 和 Running 互斥
- 从 ready queue 取出后，在释放锁前标记 Running
- 被唤醒任务只入队一次，陈旧 queue entry 不会导致双跑
- exit/reap 不销毁仍被另一 CPU 引用的 TCB、内核栈或地址空间

建议在 debug 构建加入 owner CPU、queue membership 和状态转换断言。

### 上下文切换锁边界

- 位置：两个 scheduler impl 的 `__switch` 调用路径。
- 待改：不能持自旋锁切换到另一任务栈，否则解锁责任会落在错误上下文。切换前固定 current/next 所有权，释放 scheduler lock，再执行架构切换。
- 中断到达、主动 yield、阻塞、sleep、exit 和首次 `run_first_task` 都要遵守同一规则。

### 抢占、唤醒和负载均衡

- 正确性阶段：允许全局 ready queue，无任务的 CPU 进入 idle，下一次本核 tick 再取任务。
- 性能阶段：增加 reschedule IPI 或明确的唤醒目标，避免 7 个 CPU idle 而 BSP 队列积压。之后再评估 per-CPU queue、work stealing 和 affinity。
- `sched_getaffinity/setaffinity` 必须与可调度 CPU 集合一致，不能报告多核却始终只在 CPU 0 运行。

## 4. Trap、timer、IPI 和架构上下文

### 每核 trap 初始化

- 位置：`wateros-platform/platform-arch/arch-impl/impl-riscv64` 与 `impl-loongarch64` 的 trap/interrupt 模块。
- 待改：每个 CPU 设置自己的 trap vector、scratch、内核栈与允许访问用户页的状态。确认 trap frame 不引用全局 current task。

### 每核 timer

- 位置：`os/src/main.rs:249-252`、`372-374` 和各平台 timer impl。
- 现状：只有 BSP 启动路径设置一次 timer deadline。
- 待改：每个 online CPU 独立开启 timer interrupt、设置下一 deadline，并在 trap 后重置本核 timer。时间源保持全局单调，调度 tick 归本核。

### IPI

最低需要：

- reschedule/wakeup IPI，或一个不会长期丢失并行度的等价机制
- TLB shootdown IPI
- CPU stop/panic 协调

IPI handler 不能获取会由被中断代码长期持有的锁。应定义 pending bit 和处理顺序。

### 架构上下文与 TLS

glibc 和 rustc 会使用线程本地存储。需要核对用户 `tp` 或 LoongArch 对应寄存器与内核 CPU-local 指针的保存恢复，避免把 CPU-local 方案和用户 TLS 绑定到同一个未经切换的寄存器。

## 5. 全局注册表和 UP 容器

### `UniprocessorSafeCell` 本身

- 位置：`os/components/wateros-base/src/sync/uniprocessor.rs`
- 现状：内部是 `RefCell<T>`，并通过 `unsafe impl Sync` 暴露给全局状态；文件注释明确要求单核或外部互斥。
- 原则：不要把它直接改名为 SMP 容器。逐个调用点选择 `Mutex`、`RwLock`、原子、只读初始化对象或 per-CPU 数据，以便审查锁粒度和锁序。

### 必须替换的已知位置

| 子系统 | 位置 | 当前对象 | 初始改法 |
|---|---|---|---|
| task | `task-impl/impl-core/src/lib.rs:33-48` | process registry | IRQ-safe spin mutex，重活移到锁外 |
| scheduler | 两个 scheduler impl 的 `src/lib.rs` | scheduler | 全局调度锁加 per-CPU current |
| mm | `mm-frame-alloctor/.../impl-stack/src/lib.rs:221-246` | frame allocator | spin mutex，后续可分片/per-CPU cache |
| vfs | `wateros-vfs/src/fd.rs:16-24` | per-task fd registry | spin mutex，避免持锁做 IO/drop |
| vfs | `wateros-vfs/src/cwd.rs:22-38` | cwd registry | spin mutex |
| vfs | `impl-fs-bridge/src/mount_table.rs:95-104` | mount namespace registry | spin/RwLock，定义与 mount table 锁序 |
| cred | `cred-impl/impl-root/src/lib.rs:204-210` | credential registry | spin mutex |

还要审查所有 `static mut Option<fn>`、全局裸 `&'static mut` 和一次性回调注册。它们如果只在 BSP 初始化后只读，可以改为 Once 或明确的初始化屏障；如果运行期会变化，必须加锁。

## 6. 内存管理和地址空间

### frame allocator

- 现状：全局 stack allocator 使用 `UniprocessorSafeCell`。
- 待改：所有 alloc/dealloc/refcount 路径加跨核同步；检查 page fault、fork、munmap 和地址空间 drop 是否在持 process/scheduler 锁时进入 frame lock，建立统一锁序。
- 性能阶段可增加 per-CPU 小缓存，但回收和统计仍要保持全局一致。

### 内核全局地址空间

- 位置：`mm-impl/impl-sv39/src/kernel_global.rs`、`impl-loongarch64/src/kernel_global.rs`
- 现状：通过全局裸可变引用访问内核地址空间。
- 待改：BSP 建好后尽量冻结内核页表；运行期映射修改需要锁和跨核 TLB shootdown。AP 上线前安装同一内核地址空间 token。

### 用户地址空间并发

`CLONE_VM` 线程可在多核同时 page fault、mmap、munmap、mprotect 和 brk。需要为每个地址空间提供锁或更细的数据结构保护，并处理：

- 同一缺页被两核同时填充
- 一核 unmap，另一核仍在用户拷贝或执行
- page table frame 的生命周期
- COW/refcount 原子性
- exec 替换地址空间时停止或退出同进程其它线程

### TLB shootdown

两个架构都不能只 flush 当前 CPU。建议设计地址空间 generation 加 IPI ack，或先采用停止其它运行该地址空间 CPU 的保守方案。释放物理页之前必须确认所有相关 CPU 已失效旧 TLB 项。

### 8 GiB 内存

- 位置：LoongArch `os/src/main.rs:335` 把 `usable_end_ppn` 截到 4 GiB。
- 待改：确认 QEMU 内存可能分段、物理地址宽度、direct map 和 DMA 限制。即使暂时只用低 4 GiB，也应让 `/proc/meminfo`、OOM 行为和设计文档准确，不应默报 8 GiB 可用。

## 7. 内核堆

### 递归分配检测 `HEAP_GUARD_DEPTH`

- 位置：`os/components/wateros-runtime/runtime-heap-allocator/src/interrupt_guard.rs:9-30`
- 现状：depth 是全局 `AtomicUsize`。进入 allocator 时加一，大于 0 就 panic。
- 多核问题：核 B 会看到核 A 的 depth 为 1，把跨核并行分配误判成同调用栈递归。
- 待改：depth 改成 per-CPU；allocator 后端继续用自己的跨核锁串行化元数据；明确顺序为本核递归检查、保存并关闭本核中断、获取 heap lock、操作、解锁、恢复中断。
- panic 或 unwind 不适用于当前内核，所有提前失败路径都必须恢复 depth 和中断状态，最好使用不分配的 RAII guard。

### 堆容量与争用

BuildStorm 会产生大量 task、fd、path 和缓存对象。检查固定 `HEAP_SPACE` 容量是否足够；记录 OOM 高水位。性能阶段测 heap lock 等待，再考虑 per-CPU slab 或 size class，不能在没有数据时先重写 allocator。

## 8. VFS、文件系统和伪文件系统

### fd、cwd、mount namespace 和 cred

这些 per-task registry 目前含 UP 容器。替换锁后还要缩短临界区：

- 不持 registry lock 调用 ext4、page cache、socket 或 handle `drop`
- fork/clone 的共享与复制操作有一致快照
- close/dup/exec/exit 不与另一核同一 task 的 fd 操作产生 UAF
- mount namespace 与 cwd path resolve 的锁序固定

### page cache 和 ext4

- page cache 已广泛使用 `spin::Mutex`/`RwLock`，但这只证明局部有锁，不证明组合路径无死锁。
- 审查 `files -> entry -> state -> ext4/block` 的既有锁序，所有新 SMP 路径保持一致。
- ext4 small read cache、根文件系统对象和块设备句柄可能形成全局串行点。先用并发读写正确性测试，再 profile rustc 小文件负载。

### procfs

除 CPU 数外，BuildStorm 还要求真实 `/proc/uptime`。CAgent 的网络统计需要 `/proc/net/tcp` 或兼容工具接口。procfs 回调读取 task、mount、cred 和 MM 时应取得短快照，不能嵌套持有多个全局 registry 锁。

### tmpfs

`/tmp` 的 heap-backed tmpfs 主路径已存在，但仍需完成 `docs/todo/fs-ramfs-tmpfs.md` 中 fd/cwd/page-cache 联调。十个 CAgent 用例并发写 `/tmp`，cargo 也会大量创建和 rename 临时文件。

## 9. 设备、网络、日志和随机数

### 块设备

块设备表和句柄已有 mutex，但 virtio queue、中断模式、DMA buffer、block cache manager 和 flush 路径仍要用 8 核并发 IO 验证。禁止在持块设备锁等待会依赖另一 CPU 调度的事件。

### 网络栈

`NETWORK_STACK` 是一个包住完整 smoltcp 状态的全局 mutex。正确性阶段可保留；socket syscall、poller task 和多个 CAgent 连接会争用它。要检查阻塞等待时已经释放网络锁，并为 `/proc/net/tcp` 提供只读快照。

### 串口和日志

多核日志行需要原子化，避免字符交错。panic 路径不能等待由已停 CPU 持有的日志锁。release 测试关闭高频 syscall/trap 日志，否则 8 核编译会被串口吞吐限制。

### 随机数和全局计数器

原子 inode/socket id 可以跨核使用，但要核对 wrap 和内存序。`/dev/urandom` 当前原子状态只适合兼容性，不应声称具备密码学质量。工具链只要求稳定读取时，也要避免各核生成完全相同序列。

## 10. 锁规则和中断规则

改造前先维护一张锁序表，至少覆盖：

1. scheduler/process registry
2. per-task fd/cwd/cred/mount registry
3. address space/frame allocator
4. page cache/ext4/block device
5. socket registry/network stack

基本规则：

- 关本核中断只能防本核重入，不能替代跨核锁。
- 自旋锁内不 sleep、不调度、不执行可能 page fault 的用户拷贝、不做慢 IO。
- 不持 scheduler lock、process registry lock 或 fd registry lock 销毁大型对象。
- irq handler 使用的锁必须有明确 IRQ-safe 获取方式，或改成原子 pending 状态。
- debug 构建记录 CPU id、lock class 和持锁状态，尽早发现反序。

## 11. 验证清单

### 启动

- [ ] RISC-V64 与 LoongArch64 都以 `-smp 8 -m 8G` 启动
- [ ] 8 个 CPU 使用不同 boot/kernel stack
- [ ] 全局初始化只执行一次，8 个 CPU 都进入 idle 或运行任务
- [ ] `/proc/cpuinfo`、affinity mask 和 `nproc` 一致报告 8

### 调度和同步

- [ ] 任务 owner 断言证明无双跑
- [ ] 8 核 yield/sleep/wakeup/exit 压测无丢任务和死锁
- [ ] pthread clone、TLS、futex、robust list 和 clear_child_tid 通过
- [ ] CAgent 十任务并发运行稳定

### 内存

- [ ] 并发 page fault、mmap/munmap/mprotect/brk 通过
- [ ] TLB shootdown 有跨核确认，释放页后无 stale mapping
- [ ] frame refcount、地址空间 drop 和 exec 多线程场景通过
- [ ] BuildStorm 期间无 OOM，内存统计与实际可用范围一致

### IO 和性能

- [ ] 并发创建、rename、truncate、unlink、fsync 和 mmap 文件一致
- [ ] page cache、ext4、block cache 锁序压测无死锁
- [ ] `/proc/uptime` 单调且不受 wall clock 改动影响
- [ ] BuildStorm 连续至少 3 次成功，并记录中位耗时和波动
