# 文档规范 Prompt

本文件描述 WaterOS 中广义文档的写法，包括 Markdown、代码注释、Rust 文档注释、commit 信息和 PR 信息。

## Markdown 文档

- 优先使用中文说明，必要时保留英文术语、crate 名、feature 名和路径。
- 先写用途，再写事实来源，再写结构或步骤。
- 涉及组件时，优先按组件拆分章节。
- 涉及未完成能力时，要明确写出当前状态和缺口。

## 普通代码注释

- 注释用于解释目的、限制和边界，不用于重复代码字面含义。
- 临时实现、占位逻辑、兼容策略和硬件假设应有注释说明。
- 涉及地址范围、页大小、中断、平台约束时应优先写清来源或假设。

## Rust 文档注释

- `pub` 暴露的 trait、类型、错误、常量、函数优先补齐 `///`。
- 模块级说明使用 `//!`，用于解释该文件或模块的职责。
- 文档注释应描述语义契约，不只描述实现细节。
- 对临时实现也要写清“当前行为”和“后续替换点”。

### 覆盖范围（避免只写聚合层）

注释与 rustdoc 的扫查范围是**路径上的全部源码**，而不是「仅一级组件聚合 crate」或「仅当前默认 feature 会编进来的 crate」。

具体要求：

- **`os/components/**`** 下每一个独立 `Cargo.toml` 所对应 crate 的 **`src/`**（及 crate 内其它 `.rs` 路径）均应覆盖；包括 **`api-v0`**、所有 **`impl-*`**（含 **`impl-dummy`**）、未挂 feature 的叶子子 crate。
- **`os/src/`**、**`user/`** 中与构建或运行约定相关的文件同上。
- **汇编、内联汇编、链接脚本**：无法用 `///` 处，用该文件惯例的注释写清与 Rust 侧结构体布局、符号名、调用约定的对应关系（参见各 `trap.asm` 与 `TrapContext` 一类注释模式）。
- Agent **不得**因「根 `wateros` 未直接依赖」「默认 feature 未启用」而跳过子目录；若本地 `cargo check` 默认不编译某路径，仍应为其补注释，并在验证说明中注明使用了哪组 `--features` / `--target`。

## Commit 信息

WaterOS 默认采用 Conventional Commits，并保留 `api(scope)` 作为核心开发专用类型。

格式：

```text
<type>(<scope>): <subject>
```

常用类型：

- `feat`
- `fix`
- `refactor`
- `docs`
- `test`
- `chore`
- `api`

## PR 信息

PR 标题应与 commit 风格一致，描述中至少包含：

- 变更类型
- 涉及组件
- 简要说明
- 与 API 的关系
- 测试方式
- 检查清单

## Mermaid 图

- 节点名使用无空格标识符。
- 总图只描述主关系，细节图再按组件拆开。
- 不在图中表达未确认的依赖关系。
- 当图描述当前快照时，应与 `os/Cargo.toml`、组件 `Cargo.toml` 和聚合 `src/lib.rs` 保持一致。
