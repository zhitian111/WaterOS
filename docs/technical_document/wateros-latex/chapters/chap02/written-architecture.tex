\chapter{总体架构设计}


\section{组件化分层}

\wateros{}按依赖方向分成三层：底层接平台和硬件，中层管内核资源，上层给用户态可见的ABI与系统调用语义。RISC-V64与LoongArch64的差异留在platform、driver和mm各自的\code{impl-*}里；task、fs、vfs、ipc和syscall等上层模块共用同一套聚合接口。

\begin{longtable}{>{\raggedright\arraybackslash}p{3.0cm}>{\raggedright\arraybackslash}p{4.7cm}>{\raggedright\arraybackslash}p{5.8cm}}
 \caption{WaterOS组件化分层}\label{tab:component-layers}\\
 \toprule[1.5pt]
 层次 & 主要组件 & 设计含义 \\
 \midrule[1pt]
 平台与运行时层 & platform、runtime、driver & 启动入口、trap汇编、定时器、中断、固件调用、控制台、开发日志、堆和设备发现；把QEMU与ISA差异收成内核内部接口。 \\
 内核资源层 & mm、task、fs、vfs、ipc & 地址空间、物理页、任务生命周期、调度、根文件系统、路径视图、fd表、pipe、waitqueue、futex和signal等核心资源。 \\
 用户接口层 & abi、syscall、cred、klog & Linux generic 64-bit系统调用编号、参数传递、错误码、凭证扩展点，以及\syscall{syslog}可读的内核日志环。 \\
 \bottomrule[1.5pt]
\end{longtable}

根crate\code{wateros}按feature聚合一级组件；各组件内部再拆\code{api-v0}、\code{impl-*}和聚合\code{lib.rs}。契约写在API crate，实现落在impl crate，聚合层按feature选出当前active impl后对外只暴露稳定模块名，例如 \code{mm::}、\code{vfs::}、\code{ipc::}。目录树与下表从源码布局与模块边界两个角度描述同一套组织方式。


\section{代码结构}

内核源码主体在\code{os/}；仓库根\code{Makefile}封装常用构建入口。平台配置、feature开关、脚本和组件实现都收在\code{os/}内，由根\code{Cargo.toml}统一聚合。

\begin{textcode}
wateros
|-- Makefile                    # 顶层构建入口
`-- os                          # 内核源码与构建主体
|   |-- Cargo.toml              # 根crate、feature与workspace配置
|   |-- Makefile                # 内核构建与运行入口
|   |-- build.rs                # 构建脚本
|   |-- config.conf             # 当前启用的feature选择（可编辑）
|   |-- feature-tree.txt        # workspace全量feature树（只读参考）
|   |-- src
|   |   |-- main.rs             # kernel_main与平台启动主线
|   |   |-- trap_handler.rs     # trap/syscall入口桥接
|   |   |-- user_bringup_*.rs   # 用户程序与测试脚本bring-up
|   |   `-- self_tests/         # 内核自检入口
|   |-- components              # WaterOS组件化内核模块
|   |   |-- wateros-base        # 地址类型、同步原语等基础定义
|   |   |-- wateros-platform    # 平台、架构、固件抽象
|   |   |-- wateros-runtime     # 控制台、日志、panic、堆
|   |   |-- wateros-mm          # 页表、帧分配、ELF装载
|   |   |-- wateros-task        # 任务、调度、等待与生命周期
|   |   |-- wateros-driver      # DTB/PCI、VirtIO、块/字符/网络设备
|   |   |-- wateros-fs          # devfs、rootfs、ext4、procfs
|   |   |-- wateros-vfs         # 路径视图、fd表、cwd、页缓存
|   |   |-- wateros-syscall     # 系统调用分发与实现
|   |   |-- wateros-abi         # errno、返回值、syscall编号
|   |   |-- wateros-ipc         # pipe、waitqueue、futex、signal
|   |   |-- wateros-cred        # uid/gid与凭证生命周期
|   |   `-- wateros-klog        # 内核日志环与syslog(2)
|   |-- scripts                 # QEMU、GDB、构建和日志脚本
|   `-- vendor                  # 离线依赖源码
\end{textcode}

\code{os/src/main.rs}负责启动顺序与组件编排；具体能力由\code{os/components/}下各crate提供。根crate本身只做feature组合、trap桥接和bring-up总线挂载。

\section{API与实现解耦}

大多数一级组件遵循三步组织：

\begin{enumerate}
 \item \code{api-v0}定义稳定契约：trait、错误类型、句柄和公共数据结构。
 \item \code{impl-*}承载具体实现，例如\code{impl-sv39}、\code{impl-qemu-riscv64-opensbi}、\code{impl-ext4-rs}。
 \item 组件根\code{src/lib.rs}按feature绑定active impl，向上再导出统一模块名。
\end{enumerate}

上层代码只依赖聚合门面，不直接引用具体impl crate。系统调用经\code{wateros-vfs}与\code{wateros-fs}公开接口访问路径和fd；\code{wateros-task}不反向依赖\code{wateros-cred}，凭证继承与清理由syscall或bring-up调用点触发。


\section{启动主线}

两条QEMU路径的组件编排顺序一致，差异只在引导参数解析、LoongArch建页表前关MMU，以及驱动发现总线类型：

\begin{enumerate}
 \item 平台汇编把控制权交给\code{kernel\_main}：RISC-V64接收OpenSBI的hart id与DTB物理地址，LoongArch64接收\code{argc/argv/envp}，其中\code{envp}常作固件信息指针。
 \item 初始化runtime，console、logging、klog、heap与\code{platform::arch}；RISC-V64在此后、LoongArch64在此前分别调用\code{driver::init\_when\_boot}传入DTB/envp指针。
 \item 在MM激活分页之前注册\code{task::init}与\code{trap\_handler::init}，保证页故障和定时器trap有路由。
 \item LoongArch64额外调用\code{platform::arch::paging::init\_paging\_disable\_mmu}，确认后续页表构建与PCI ECAM/MMIO使用直接寻址。
 \item \code{mm::kernel\_mm::init}建立内核地址空间；驱动成功则进入\code{driver::active\_impl::init\_after\_boot}。
 \item \code{fs::init}探测块设备并注入实现；\code{user\_bringup\_bus::run}在总线内RW挂载ext4根卷并串行执行bring-up阶段。
 \item 打开定时器与全局中断，\code{task::run\_first\_task}把CPU交给就绪任务，后续执行由trap/syscall路径驱动。
\end{enumerate}

具体分页格式、DTB保留策略、网络栈烟测和\code{self\_tests}调用见第1章实现摘要与第3章模块实现；本章只固定组件之间的先后关系。


\section{Feature组合与平台构建}

\wateros{}用Cargo feature管理平台差异。根\code{os/Cargo.toml}定义\code{qemu-riscv64-opensbi}，默认与\code{qemu-loongarch64-virt}两组互斥组合；二者都拉起完整I/O栈，含 driver、fs、ipc、cred、vfs-bridge、klog 与 \code{syscall/impl-kernel}，只在platform、mm页表实现和VirtIO总线上分叉。

\begin{tomlcode}
[features]
default = ["qemu-riscv64-opensbi"]
impl-sv39 = ["mm/impl-sv39"]

qemu-riscv64-opensbi = [
  "abi/impl-linux-generic64",
  "dep:cred", "dep:driver", "dep:fdt", "dep:fs", "dep:ipc",
  "driver/impl-block-cache",
  "driver/impl-qemu-riscv64-opensbi",
  "ipc/all",
  "vfs-bridge",
  "impl-sv39",
  "mm/vfs-root-read",
  "platform/impl-qemu-riscv64-opensbi",
  "runtime/impl-info",
  "dep:klog", "klog/default",
  "runtime/impl-platform-console",
  "syscall/impl-kernel",
]

qemu-loongarch64-virt = [
  "abi/impl-linux-generic64",
  "dep:cred", "dep:driver", "dep:fdt", "dep:fs", "dep:ipc",
  "driver/impl-block-cache",
  "driver/impl-qemu-loongarch64-virt",
  "ipc/all",
  "mm/impl-loongarch64",
  "mm/vfs-root-read",
  "platform/impl-qemu-loongarch64-virt",
  "runtime/impl-debug",
  "dep:klog", "klog/default",
  "runtime/impl-platform-console",
  "syscall/impl-kernel",
  "vfs-bridge",
]
\end{tomlcode}

除根\code{Cargo.toml}里的平台组合外，组件级\code{api-*}与\code{impl-*}选择还依赖各crate的\code{default} feature。\code{make configure}会同时生成两份快照，职责不同：

\begin{itemize}
 \item \code{feature-tree.txt}：workspace\emph{全量}feature树。按package列出所有已定义的feature及其向下传递链，用于查``有哪些可选组合、feature如何传递''，不代表当前编译实际选中哪条路径。
 \item \code{config.conf}：\emph{当前正在使用}的feature选择。未注释行对应当前各\code{Cargo.toml}里\code{default}已启用的项；编辑后经\code{make apply\_features}写回manifest，才是改组件实现的入口。
\end{itemize}

Makefile目标见下文\ref{sec:feature-config-make}。下面各举一条从根到叶子impl的传递示例，摘自全量树中的RV/LA主线：

RISC-V64块设备链：

\begin{textcode}
qemu-riscv64-opensbi
  -> driver/impl-qemu-riscv64-opensbi          # wateros-driver
       -> block/impl-virtio-mmio                 # wateros-driver-block
            -> wateros-driver-block-impl-virtio-mmio
\end{textcode}

同一条组合里，平台与架构链为\code{platform/impl-qemu-riscv64-opensbi}拉入\code{arch/impl-riscv64}和\code{firmware/impl-riscv64-opensbi}；页表链为根\code{impl-sv39}到\code{mm/impl-sv39}。

LoongArch64块设备链：

\begin{textcode}
qemu-loongarch64-virt
  -> driver/impl-qemu-loongarch64-virt          # wateros-driver
       -> block/impl-virtio-pci                  # wateros-driver-block
            -> wateros-driver-block-impl-virtio-pci
\end{textcode}

对应平台链为\code{platform/impl-qemu-loongarch64-virt}拉入\code{arch/impl-loongarch64}与\code{firmware/impl-qemu-loongarch64-uart16550}；页表链为\code{mm/impl-loongarch64}。两条路径的syscall、vfs、task和fs注册表feature相同，替换点集中在platform-arch、driver-impl和mm-impl。

\subsection{当前启用的feature，config.conf}\label{sec:feature-config-conf}

\code{config.conf}记录并编辑\emph{当前实际使用}的feature：\code{make configure}读取各crate现有\code{default}，把已启用项写成未注释行、未启用项写成\code{\#}注释行。改配置、\code{make apply\_features}、再编译，才是切换组件\code{impl-*}的常规流程；全量树里能看到但未在\code{config.conf}中启用的feature，不会进入当前构建。

\begin{itemize}
 \item 未注释行表示启用；行首\code{\#}表示禁用。
 \item crate名以冒号结尾，例如 \code{wateros-driver:}；其下缩进两格的是该crate可选feature。
 \item 只导出非\code{api-v0}/\code{impl-*}命名的workspace crate；\code{*-api-v0}与\code{*-impl-*}叶子crate不出现在树中。
 \item 根\code{wateros:}下列出全部根feature，含 \code{qemu-riscv64-opensbi} 等平台组合；组件crate下列\code{api-v0}、\code{impl-*}等可替换项。驱动子系统允许同时启用多个\code{impl-*}，例如块设备MMIO与PCI桩并存于配置树，实际生效仍受平台feature约束。
\end{itemize}

文件头与根crate片段示例如下，完整文件见 \code{os/config.conf}：

\begin{textcode}
# WaterOS config.conf (只导出非 api/impl crate)
# 规则：未注释行 = 启用；以 # 开头 = 禁用。
# 结构：crate 行以 ':' 结尾；其下缩进两格的是 feature。

wateros:
  # qemu-loongarch64-virt
  qemu-riscv64-opensbi
  wateros-driver:
    api-v0
    wateros-driver-block:
      api-v0
      impl-virtio-mmio
      # impl-virtio-pci
  wateros-task:
    api-v0
    impl-core
    impl-multi-class
    # impl-round-robin
\end{textcode}

典型工作流：需要\emph{查看}可选组合时读\code{feature-tree.txt}；需要\emph{修改}当前实现时编辑\code{config.conf}。改配置前先\code{make configure}与manifest对齐；注释/取消注释目标feature后\code{make apply\_features}写回\code{default}，各 \code{Cargo.toml} 同目录会备份 \code{Cargo.toml.wosbak}，撤销用\code{make revert\_features}。

案例：把\code{wateros-task}下\code{impl-round-robin}取消注释、并注释掉\code{impl-multi-class}，执行\code{make apply\_features}后重新\code{make rv\_check}，task调度器default会指向round-robin实现。切换QEMU平台时，在\code{wateros:}下注释当前\code{qemu-riscv64-opensbi}、启用\code{qemu-loongarch64-virt}，apply后再\code{make la\_check}验证LoongArch组合能否通过静态检查。日常 \code{make kernel-la} 仍显式传入 \code{qemu-loongarch64-virt}，与根 \code{default} 是否一致无关。


\subsection{Makefile与feature相关命令}\label{sec:feature-config-make}

\code{os/Makefile}把平台feature写死在编译变量里，同时提供配置文件的生成、应用与回滚目标。相关用法如下：

\begin{longtable}{>{\raggedright\arraybackslash}p{3.6cm}>{\raggedright\arraybackslash}p{10.0cm}}
 \caption{Makefile中与feature相关的目标}\label{tab:make-feature-targets}\\
 \toprule[1.5pt]
 目标 & 作用 \\
 \midrule[1pt]
 \code{configure} & 扫描全部\code{Cargo.toml}：生成全量\code{feature-tree.txt}，并按当前\code{default}导出\code{config.conf}。 \\
 \code{apply\_features} & 读取\code{config.conf}中启用的行，写回各crate的\code{default} feature，并备份 \code{.wosbak}；此后构建按新选择编译组件。 \\
 \code{apply\_features\_la} & 同\code{apply\_features}，但读取\code{config-loongarch64.conf}，需自行维护该文件。 \\
 \code{revert\_features} & 从各目录的\code{Cargo.toml.wosbak}恢复\code{Cargo.toml}。 \\
 \code{kernel-rv} / \code{kernel-la} & 编译时分别传入\code{--features qemu-riscv64-opensbi}或\code{--no-default-features --features qemu-loongarch64-virt}。 \\
 \code{rv\_check} / \code{la\_check} & \code{cargo check}，feature与上两行编译变量一致。 \\
 \code{kernel-rv-ltp-glibc}等 & 在RV/LA编译flag上追加\code{bringup-ltp-glibc-only}或\code{bringup-ltp-musl-only}根feature。 \\
 \bottomrule[1.5pt]
\end{longtable}

命令行案例：

\begin{bashcode}
cd os

# 1. 扫描 Cargo.toml：导出全量 feature 树 + 当前启用的 config.conf
make configure

# 2. 查传递关系 → 看 feature-tree.txt
#    改当前 impl 选择 → 编辑 config.conf，再 apply
make apply_features

# 3. 按 Makefile 绑定的平台 feature 编译 / 检查
make rv_check          # RISC-V，--features qemu-riscv64-opensbi
make kernel-rv
make la_check          # LoongArch，--no-default-features + qemu-loongarch64-virt
make kernel-la

# 4. 仅 LTP 长跑：追加 bringup-ltp-* 根 feature
make kernel-rv-ltp-glibc
make rv_qemu_run       # 仍使用 kernel-rv 产物

# 5. 放弃 apply 改动，恢复 Cargo.toml
make revert_features
\end{bashcode}

说明：\code{configure}不修改源码，只刷新全量树并同步\code{config.conf}与manifest的一致性。\code{apply\_features}只消费\code{config.conf}，不改\code{feature-tree.txt}。\code{kernel-rv}/\code{kernel-la}的平台feature仍由Makefile显式传入；\code{config.conf}管的是组件级\code{default}，调度器、块设备后端、日志级别等。二者叠加后才是某次\code{cargo build}实际链入的impl。

\section{内核入口代码流程}

\code{os/src/main.rs}按board feature分别编译两个\code{kernel\_main}，共享``runtime与arch先就绪，trap在分页前注册，驱动与FS在地址空间建立后初始化，最后开中断进调度''的骨架。下面摘录体现双架构差异的关键片段，省略日志、烟测和网络初始化等实现细节。

RISC-V64入口在解析引导参数后，先探测DTB再进入runtime初始化：

\begin{rustcode}
#[cfg(feature = "qemu-riscv64-opensbi")]
pub fn kernel_main(boot_arg0: usize, boot_arg1: usize) -> ! {
    let _boot_context = BootContext::from(BootArgs::new(boot_arg0, boot_arg1));
    driver::init_when_boot(boot_arg1);
    // runtime::console / klog / logging / heap ...
    platform::arch::init();
    task::init();
    crate::trap_handler::init();
    // mm::kernel_mm::init ...
    if driver::active_impl::init_after_boot().is_ok() {
        fs::init();
        crate::user_bringup_bus::run();
    }
    // enable timer interrupt ...
    task::run_first_task()
}
\end{rustcode}

LoongArch64入口参数不同，且在MM初始化前显式关闭固件遗留分页：

\begin{rustcode}
#[cfg(feature = "qemu-loongarch64-virt")]
pub fn kernel_main(_argc: usize, _argv: usize, envp: usize) -> ! {
    // runtime init ...
    platform::arch::init();
    driver::init_when_boot(envp);
    task::init();
    crate::trap_handler::init();
    platform::arch::paging::init_paging_disable_mmu();
    // mm::kernel_mm::init (usable_end_ppn capped) ...
    if driver::active_impl::init_after_boot().is_ok() {
        fs::init();
        crate::user_bringup_bus::run();
    }
    task::run_first_task()
}
\end{rustcode}

两条路径都把\code{trap\_handler}注册放在\code{mm::kernel\_mm::init}之前，把\code{user\_bringup\_bus}放在驱动与\code{fs::init}成功之后；定时器与全局中断在\code{run\_first\_task}之前打开。完整调用顺序以\code{os/src/main.rs}为准。
